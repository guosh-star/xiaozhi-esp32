## 2. 2026-10-24 设备端

### 2.1 32kHz 稳定性与 STAT 诊断字段

- 涉及：`cuckoo_part2.cc`、`audio_service.cc/.h`
- 新增 STAT（每 8 秒）：
  ```
  state fill underrun samp mix late max_gap wait_late max_wait
  write_late max_write clip music_peak out_peak dl rate heap sram
  ```
- 关键结论：
  - `write_late=0`、`max_write=0ms`：写入 I2S 从不迟到
  - `underrun=0`：背景音频环形缓冲从未欠载
  - I2S DMA = 8×511 帧 ≈ **128ms @32kHz**，`wait_late` 31–35ms 抖动不足以造成可听断裂
  - 纯聆听窗口 `clip=0`、`out_peak=music_peak`：聆听撕裂不是混音级数字削波
  - 含 TTS 的窗口会出现 `clip>0`（TTS + 音乐同时满刻度），属另一个问题（见 5）

### 2.2 放歌不再压低硬件音量

- 文件：`cuckoo_part2.cc`（`PlayOpus` 路径）
- 改动：删除 `music_vol = old_vol * 80 / 100`，保持音量 **80（-10dB）**
- 日志：`PlayOpus: keep volume 80 (no AEC reduction)`
- 原因：压低音量对 AEC 参考没有实质帮助，反而让音乐听起来变小；AEC 参考采集保留。

### 2.3 上行静音实验（定位撕裂来源）

- 新增 API：`AudioService::SetUplinkMuted(bool)`（清空 `audio_send_queue_`）
- 实验：整首歌关闭上行发送
- 用户主观结果：
  - 聆听段变轻
  - idle 完全干净
- 结论：
  - **WiFi 上行发射是撕裂原因之一**
  - 但不是唯一原因：不发包时 AFE（AEC/NS/AGC）与 Opus 编码仍在跑，残余推断为 DSP 负载/电源耦合
- 该 API 保留，用于后续对照实验。

### 2.4 WiFi 自适应发射功率（三版演进，最终 B）

#### V1：本地 VAD 触发（失败）
- 逻辑：`on_vad_change(speaking)` → 80；静音 3 秒 → 12
- 结果：放歌时本地 AFE VAD **一次都没触发**（日志无 `boost 80 (vad)`），状态机的 speaking 是服务器识别结果驱动的
- 结论：VAD 在音乐环境下不可靠

#### V2：AEC 后 RMS 能量触发（失败）
- 逻辑：`OnOutput` 计算处理后 PCM 的 RMS，`>600` → 80 + 日志 `boost 80 (energy, rms=xxx)`
- 实测：
  - 说话 RMS：679–5629
  - 用户静默 >10 秒时，音乐残响/环境噪声 RMS 仍为 **620–2508**
  - 两者区间重叠，单阈值无法区分 → 静默时持续误 boost，无法降回 12
- 结论：放弃 RMS 方案，移除能量 boost（`on_voice_energy` 回调和 `last_energy_cb_us_` 字段保留，未使用）

#### V3（最终）：服务器 speaking 状态触发（B 方案）
- 逻辑：
  - 播放循环读取 `app.GetDeviceState()`
  - `kDeviceStateSpeaking` / `kDeviceStateConnecting` → 刷新 `last_voice_seen`，目标功率 80
  - 离开 speaking 后保持 **5 秒**，再降回 12
  - **只由播放循环一个写入点**控制功率，避免双写竞态
- 日志：
  ```
  WIFI-TX: 80 -> 12 (silent)
  WIFI-TX: 12 -> 80 (server speaking)
  WIFI-TX: 80 -> 12 (silent)
  ```
- 修复的竞态：
  - 旧版 `SetDeviceState` 和播放循环都写功率，出现同一毫秒 `boost 80` → `80 -> 12` → 1 秒后才 `12 -> 80`
  - 修复后删除 `SetDeviceState` 的 boost，只保留循环写入；验证日志无同毫秒回降
- 代价：开口前 1–2 秒仍是 3 dBm；由于设备到路由 RSSI **-33 dBm**，上行链路很强，实际不影响识别
- 低功率值：**12（3 dBm）**；若后续想再降干扰，可试 **8（2 dBm）**（未实施）

### 2.5 BOOT 提示音混入背景音乐

- 文件：`cuckoo_board.cc`、`application.cc`、`audio_service.cc/.h`
- 问题：放歌时按 BOOT，`ask` 提示音走 `OutputRawPcm` 会打断歌声
- 修复：
  - `ask.pcm` 16kHz → 32kHz 重采样
  - 放歌时 `MixIntoBackgroundAudio(resampled, d, 0.9f)` 叠加到音乐
  - 之后 `vTaskDelay(pdMS_TO_TICKS(2500))` 再 `ToggleChatState()`
  - 无音乐时仍走 `OutputRawPcm`
- 日志：`BOOT: ask prompt mixed into bg audio (80642 samples)`
- 验证：多次按 BOOT 均出现该日志，提示音与音乐融合，不再切断歌声。

### 2.6 唤醒阈值 0.02

- 位置：`cuckoo_part2.cc:597`
- 说明：代码主动设置，注释写明“（IsBgAudioActive 守卫）导致 0.30 卡住，在此恢复灵敏阈值 0.02”
- 风险：容易误唤醒（实测 `prob=0.028689` 即唤醒）；目前保留，后续可结合音乐状态做动态阈值。

### 2.7 `voice_detected_` 改为 `std::atomic<bool>`

- 文件：`audio_service.h`
- 原因：VAD 回调（音频任务）与播放循环（另一任务）跨核读写，普通 bool 有竞态
- 结果：消除潜在的数据竞争；不影响 VAD 是否触发的结论（VAD 在音乐下仍不触发）。

### 3.4 服务器自动续期（2026-10-24 16:14 验证成功）

- 目标：不用电脑、不用扫码，服务器自动更新 Cookie
- 机制：
  - 用 Cookie 中的 `wxrefresh_token` / `psrf_qqrefresh_token`、`wxopenid`、`wxunionid`、`wxuin`
  - 调 `music.login.LoginServer` / `Login`，`loginMode=2`
  - POST `https://u.y.qq.com/cgi-bin/musicu.fcg`（普通接口，无需签名）
  - 返回新的 `musickey`，写回 `qm_keyst` / `qqmusic_key`，同时保存新的 `refresh_token`
- 服务端：
  - `qq_refresh_cookie()` + `qq_cookie_refresh_loop()`
  - 每 12 小时刷新一次；服务启动后 10 秒先刷一次
  - 原子写回 `qq_cookie.txt`（600）
- 实测：
  - `[qq-refresh] ok key_len=105 prefix=W_X_63`
  - 新 Cookie 1251 字节，含 `uin` + `wxrefresh_token`
  - 《达拉崩吧》周深 `duration 245.713560`，完整 VIP 版
- 备份：
  - `server.py.bak-20261024-autorefresh`
  - `qq_cookie.txt.bak-before-promote-20261024`
  - `qq_cookie.txt.bak-20261024-refresh`
- 限制：若 refresh token 本身失效/被风控，日志会报 `[qq-refresh] rejected`，此时仍可用 bat 手动扫码一次。
